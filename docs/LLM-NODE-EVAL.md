# 评估：画布里嵌「浏览器窗口节点」接网页版大模型

> 结论先说：**iframe 嵌网页这条路走不通**（对方服务器 + 浏览器策略双重限制，有实测）；
> **Electron + webview 能走通但代价大且仍违规**；真正可行的是**做 API 节点**。
> 下面把三条路的证据、代价、收益都摆出来。

---

## 一、实测：主流站点全都拒绝被嵌入

刚跑的响应头（`curl -sIL`）：

| 站点 | 关键响应头 | 能不能 iframe |
|---|---|---|
| chatgpt.com | `X-Frame-Options: SAMEORIGIN` | ❌ 不能 |
| claude.ai | `X-Frame-Options: SAMEORIGIN` + CSP `frame-src 'self'` | ❌ 不能 |
| chat.deepseek.com | 直接 `429`（本机被限流，没拿到头） | ⚠️ 未能验证，但有反爬 |
| kimi.moonshot.cn | 302 → 200，无 XFO，但 SPA 自检 `top !== self` | ❌ 会自己跳走 |
| www.doubao.com | CSP 带 report-to / upgrade-insecure | ⚠️ 靠 JS 自检拦 |
| chat.qwen.ai | 无响应头输出（被前置拦截） | ❌ 不能 |

`X-Frame-Options: SAMEORIGIN` 的含义就是「只允许同源页面嵌我」。这是**服务器说了算**，
前端改不了。

---

## 二、为什么 iframe 这条路是死的（四层拦截）

1. **响应头**：`X-Frame-Options` / CSP `frame-ancestors` —— 浏览器直接拒绝渲染，白屏。
2. **前端自检**：就算响应头没设，SPA 里普遍有 `if (window.top !== window.self) top.location = ...`，
   嵌进去会被它自己跳出去。
3. **第三方 Cookie**：Safari / Firefox 默认拦第三方 cookie，Chrome 在无痕和部分用户的
   Tracking Protection 下也拦。**就算前两层过了，也大概率登录不上**——大模型网页全都要登录。
   这一层最致命，而且我们控制不了。
4. **交互**：iframe 里的键盘、剪贴板、拖拽都受权限限制；画布还要抢 pointer 事件，
   在节点里滚页面 vs 平移画布会打架。

**结论**：这不是"难做"，是"做不成"。想绕过只能改对方响应头（见下）。

---

## 三、反向代理改写响应头：技术能过第一层，但后面三层还在

思路：`server.py` 加一个代理，把目标站响应里的 `X-Frame-Options` 删掉、CSP 改掉。

过不去的：

- **第 2 层**：SPA 的 JS 自检还在（除非再注入脚本改 `window.top`，越走越野）。
- **第 3 层**：登录态。代理域是 `127.0.0.1`，cookie 域不匹配 → 要么用户把账号密码
  交给本地代理（等于把密码存明文），要么每个请求带原始 cookie（那还不如直接用浏览器）。
- **第 4 层**：交互冲突还在。

代价还包括：

- **违反服务条款**：绕过技术保护措施 + 自动化操作网页版，账号可能被封。
- **维护成本**：对方前端改一次（改个类名、换个接口）代理就崩，等于长期跟着人家跑。
- **安全面**：本地代理转发用户凭据，一旦被别的本机程序访问就是事故。

**不建议做。**

---

## 四、Electron + `<webview>`：能通，但和这个项目的定位冲突

`<webview>` 能加载任意页面、有独立会话、能共享登录态（用户在里面正常登录）。
代价：

| 项 | 影响 |
|---|---|
| 分发方式 | 从「双击 `启动.bat` + 浏览器」变成「装一个 ~150MB 的 Electron 包」 |
| 跨平台 | 要分别打 Windows / macOS / Linux 包，还要处理签名 |
| 自动更新 | 需要一套更新通道 |
| 体积/启动 | 冷启动 2~3 秒，内存多 200MB+ |
| 合规 | **仍然违反 ToS**——本质还是"自动化操作网页版" |

**成本约 2~3 周**，而且会把项目最值钱的那点优势（零依赖、拷贝即用、`python server.py` 就能跑）
直接抹掉。**不值得。**

---

## 五、推荐：LLM 节点走 API（OpenAI 兼容协议）

这才是"能在画布里自动化"的唯一合规路径。国内几家都兼容 OpenAI 协议，一个节点通吃：

| 服务商 | base_url | 备注 |
|---|---|---|
| DeepSeek | `https://api.deepseek.com` | 最便宜，国内直连 |
| 通义千问 | `https://dashscope.aliyuncs.com/compatible-mode/v1` | 有免费额度 |
| Kimi | `https://api.moonshot.cn/v1` | 长上下文 |
| OpenAI | `https://api.openai.com/v1` | 需要代理 |
| 自定义 | 任意 | 本地 Ollama / LM Studio 也行（`http://127.0.0.1:11434/v1`） |

### 节点长什么样

```
┌─ 提示词助手 ──────────── [模型 ▾] ─┐
│ 输入：← 连进来的文本节点             │
│ ┌────────────────────────────────┐ │
│ │ 一只猫坐在窗台上，午后阳光…      │ │  ← 输出（可再连到图片节点）
│ └────────────────────────────────┘ │
│ [扩写] [精简] [翻译] [自定义…]      │
└────────────────────────────────────┘
```

- 输入口：接文本节点（草稿提示词）
- 输出：写回节点自己的文本，可连到图片节点的提示词
- 四个动作按钮，指令模板内置、可改
- 模型 / 温度 / 最大长度收在胶囊里（和生成器面板同一套交互）

### 三个关键决定

1. **key 存 `data/llm.json`（服务端），不进画布存档。**
   画布存档会被导出、会上传 GitHub——key 一旦进去就漏了。`data/` 已经在 gitignore 里。
2. **请求走 `server.py` 代理（`/api/llm`），前端不直连。**
   理由：绕开 CORS；key 不出现在浏览器 devtools / 页面内存里；以后换服务商只改一处。
3. **不做流式**（第一版）。流式要 SSE 透传，收益是"看着它打字"，成本是多一层协议。
   先做一次性返回，需要再加。

### 成本与风险

- **成本 3~5 天**：一个节点类型 + 一个代理路由 + 一个设置面板（填 key）。
- **风险**：用户需要自己的 API key（要花钱）。这是这条路唯一的门槛。
- **收益**：这是唯一能"自动化"的形态——扩写结果直接流进图片节点，不用复制粘贴。

## 六、折中方案：外链卡片节点（半天，零风险）

如果诉求只是"画布里随手能打开某个网页"，那就别嵌，做个卡片：

- 节点显示 favicon + 标题 + URL，双击用系统浏览器打开
- 可以把浏览器里复制的文字粘回画布（现有文本节点就行）
- 成本：半天；合规：完全没问题

**但它不是"节点里能用 LLM"**，只是个书签。价值有限，看你要不要。

---

## 七、我的建议

```
先做 API 节点（3~5 天）  ← 唯一能自动化、合规、且不破坏零依赖的路
外链卡片顺手做（半天）    ← 便宜，但别指望它能自动化
不做 iframe              ← 做不成
不做 Electron            ← 能成，但代价和项目定位冲突，且仍违规
```

如果你想要的是"白嫖网页版免费额度"，那这条路**技术 + 合规都不通**，我建议直接放弃——
用 DeepSeek 的 API 跑提示词扩写，一次调用成本是千分之几分钱，比折腾代理划算得多。
