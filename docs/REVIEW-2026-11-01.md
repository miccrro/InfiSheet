## 二、P0：存档里的图片该落盘，不该内联

### 2.1 现状链路

- 生成图：`artifactURL()` 返回 `/api/view?...`，**只存 URL**，很好。
- 本地编辑：4 处 `cv.toDataURL('image/png')` 直接把 base64 写进节点
  —— `app.js:8163`（旋转）、`:8282`（调色）、`:8594`（扩图落地）、`:9789`（裁剪/擦除）。
- 这些 base64 会顺着 `serialize()`（`app.js:5882` 带 `dataURL` 一起存）进入三个地方：
  1. 撤销栈：`snapshotState()` = `JSON.stringify(serialize())`，`limit: 40`（`app.js:43-53`）
  2. `localStorage`：`app.js:5972 / 6064 / 9871`，同一份 JSON
  3. 服务端 `canvas.json` / `projects/*.json`

### 2.2 实测代价

用与真实结构同构的节点（1024² PNG 的 base64 ≈ 1.4 MB）在 Node 里量 `JSON.stringify`：

| 图片数 | 存档 JSON | 单次 stringify | 40 份快照常驻 |
|---|---|---|---|
| 6 | 6.0 MB | 7.1 ms | 240 MB |
| 12 | 16.8 MB | 23.6 ms | 672 MB |
| 24 | 33.6 MB | 50.7 ms | 1344 MB |

`commit()` 有 **46 个调用点**（拖动结束、改参数、连线、删节点……）。也就是说 12 张图的工程里，
**每一次这样的操作都付一次 24 ms 的同步序列化 + 一次大字符串分配**，再叠加 40 份字符串的 GC 压力。
这正好回答了 ROADMAP「交互期性能没测」那一项：瓶颈不在渲染，在**状态序列化**。

### 2.3 建议（按性价比排序）

1. **本地编辑产物先上传再进节点**（最小改动，收益最大）
   复用现成的 `/api/upload`（`pinArtifact()` 已经在用同一条路），把 `cv.toDataURL()` 换成
   `canvas.toBlob()` → `POST /api/upload` → `n.dataURL = artifactURL(...)`。
   4 个调用点各改 5 行左右，存档立刻回到"只有 URL"的形态，撤销栈和 localStorage 一起瘦下来。
2. **快照只存结构，不存像素**
   `snapshotState()` 里把 `dataURL` 换成稳定引用（`uploaded` 文件名或 URL 本身就是稳定引用），
   撤销时按引用回填。40 份快照从 672 MB 降到几百 KB。
3. **`localStorage` 降级为索引**
   只存 `{projectId, rev, view}` 这类轻量兜底；超配额时**要提示**（现在 `catch` 里连 `flash()` 都没有）。
   顺带把 `catch { /* 超配额忽略 */ }` 换成显式分支：写失败就 `setSaveState('本地缓存已满')`。

## 三、P1：可维护性债（数字都在涨）

### 3.1 `app.js` 已经翻倍

| | ROADMAP（10-26） | 现在（11-01） |
|---|---|---|
| `app.js` | 5081 行 / 189 函数 | **9881 行 / 328 函数** |
| 最大函数 | `buildGenPanel` 259 行 | **`buildOutpaintFrame` 410 行** |

`buildOutpaintFrame`（`app.js:8627`，410 行）里同时干了：建 DOM、绑 8 个锚点、换算视图缩放、
管 `opSession`/`AbortController`、同步参数条、写存档备份（`opBackup`）。这类"一个函数一个子系统"
是后续每加一个图片工具就复制一遍的根源。

**建议**：先做 ROADMAP #2（抽纯函数到 `static/lib/graph.js`），再拆 `buildOutpaintFrame` 为
`layout / anchors / session / syncBar` 四段。顺序不能反——`pickFn()` 靠源码反射抠函数，
拆之前必须先有 import 版的测试。

### 3.2 CSS 层叠

`style.css` 3303 行，989 个唯一选择器里 **132 个重复定义**：

```
10x  #projectBar        8x  #bar            8x  #statusChip
 9x  #bar .icon        8x  #projectBar .icon.tiny
```

还有成段的历史版本叠加（`背景 v3` → `背景 v4`、两段同名 `/* ---------- 全局设置 ---------- */`）。
这类文件的特点是：**没人敢删**，只能继续往后加。

**建议**：一次纯机械的收尾——同选择器合并、被完全覆盖的旧段删除、v3/v4 只留最终版。
风险可控（e2e 有 305 条断言 + 截图比对），但要在单独一次提交里做，不和功能混。
另外在 `tools/check.mjs` 加一条：同一选择器出现 >2 次就告警。

### 3.3 服务端写盘不统一

| 写法 | 位置 |
|---|---|
| ✅ `tmp` + `os.replace` | `server.py:103`（settings）、`:1163`（MCP 配置） |
| ❌ 直接 `write_text` | `server.py:1673, 1846, 1872, 1907, 2044, 2329` |

`1846`/`1872` 正是**画布存档**（`projects/<id>.json` 与 `canvas.json`）。断电/崩溃时可能留下半个 JSON，
下次启动读 `json.loads` 直接抛异常。`archive_canvas()` 有备份，但备份的是**上一次**的内容。

**建议**：抽一个 `write_json_atomic(path, data)`，把 6 处直接写盘全部换掉（约 10 行改动）。
这是"一次投入、永久收益"的那类修复。
