# 图片生成迭代方案

> 面向"从提示词到出图"这条链路。每条都先给**代码事实**（文件行号 / 现状行为），再说改法——
> 不凭印象列待办。工程侧（测试、性能、可维护性）见 [`ROADMAP.md`](ROADMAP.md)，
> 产品侧其他能力见 [`FEATURES.md`](FEATURES.md)。

## 一、现状盘点

现在的生成链路是：面板填参数 → `buildGenGraph()` 改写 API 图 → `POST /api/run` →
`pollPrompt()` 轮询 → 产物进 `gen.gallery` 和 `gen.runs`。

已经有的（不用重做）：

| 能力 | 位置 |
|---|---|
| 提示词 / 工作流 / 画幅 / 尺寸 / 张数 | `buildGenPanel()`，参数收在胶囊里 |
| 种子（随机 / 固定两态） | `planSeed()`（`app.js:858`） |
| 参考图（连线 + `@` 引用，顺序映射到 `images.image_N`） | `refMarks()` / `bindRefImages()` |
| 多图结果翻页 | `gen.gallery` + `setGallery()` |
| 生成历史（每次一条，可看回/派生） | `gen.runs` + `openRunList()` |
| "设了不生效"如实上报 | `batchShortfall()` / `sized=false` 提示 |

缺的（下面逐条展开）：**没有队列、没有错误分类、种子只能两态、参数不能存、不能并排比、没有局部重绘**。

## 二、五个真实痛点（都有代码证据）

### 痛点 1：一次只能点一个节点

每个节点的生成是**各自独立**的：`generateImage()` 里 `postJson('/api/run')` + `pollPrompt()`。
画布上 8 个图片节点想一起出图，就得点 8 次、盯 8 个面板。

而 `#queueBadge` 看着像队列，其实只是 `flash()` 复用的提示条（`app.js:4432`）——
**没有任何队列视图**。ComfyUI 服务端本来就有队列（`/queue`），画布这层完全没利用。

### 痛点 2：出错只有一句字符串

```js
if (err) { g.status = `出错：${err}`; }        // app.js:2089
g.status = `失败：${err.message}`;              // app.js:2119
```

显存不够、模型没加载、工作流连错、超时——全都糊成一行红字。没有分类，**更没有自动重试**。
用户唯一能做的是"再点一次"，而 OOM 再点一次还是 OOM。

### 痛点 3：种子只有"随机 / 固定"

`planSeed()` 只有两支：`fixed` 用给定值，否则 `Math.random() * 2^32`。

实际调图时最常用的三种操作都做不到：

- 「这张不错，种子 +1 再来一张」（现在要手抄数字再加一）
- 「重掷」（要先切到随机、生成、再切回固定）
- 「用上一张的种子，但改提示词」（得去历史里翻出数字，手填）

### 痛点 4：参数不能存，每次重填

工作流能存进「我的工作流库」，但**面板参数不行**——画幅、尺寸、张数、种子模式、
参考图组合，换个节点就得重新点一遍。同一套"竖构图 + 2 张 + 固定种子"每次手动复现。

### 痛点 5：不能并排比

生成历史宫格能比**同一个节点**的历史，但"工作流 A vs 工作流 B"、"1K vs 2K"这种
跨节点对比没有。要么导出到文件夹自己拼，要么来回切节点靠记忆比。

## 三、三批迭代

### 第一批（P0，约 1 周）：把"能出图"变成"可靠地出图"

#### 1.1 生成队列面板

- **做**：顶栏加一个队列入口（复用 `#queueBadge` 的位置但做成可展开面板）。列出所有
  在跑/排队/完成/失败的任务：节点名 · 工作流 · 尺寸 · 进度 · 耗时。支持逐个取消、全部取消、
  失败重试。
- **技术落点**：`pollPrompt()` 已经在轮询每个 prompt_id，把它的状态写进一个
  `state.jobs` 表（`{ id, nodeId, promptId, phase, startedAt }`）即可；取消调 ComfyUI
  的 `POST /queue {"delete":[id]}`（需要新增一条透传路由，`server.py` 里加一个
  `/api/queue/cancel`，和现有 `/api/run` 同一套代理写法）。
- **验收**：3 个节点同时生成 → 队列面板出现 3 条、进度各自走、取消其中 1 条后另外 2 条继续；
  e2e 用假 ComfyUI 断言（不需要真模型）。
- **成本**：4~5 天。**风险**：低。这是纯增量，不动现有生成逻辑。

#### 1.2 错误分类 + 自动重试

- **做**：把 `err` 分四类并给不同处理：

  | 类型 | 判定 | 处理 |
  |---|---|---|
  | 显存不足 | 报错含 `out of memory` / `OOM` | 提示"降到 X 尺寸重试？"，一键降档重跑 |
  | 模型缺失 | 含 `not found` / `cuda` 加载失败 | 指出缺哪个文件，不重试 |
  | 工作流错误 | ComfyUI 返回 `error` 节点 id | 标出是哪个节点（`/history` 里有 `node_errors`） |
  | 超时/网络 | 轮询超时、连接失败 | 自动重试 1 次，再失败才报错 |

- **技术落点**：`pollPrompt()` 的错误回调里做分类（新增 `classifyGenError(msg)` 纯函数，
  好测）；降档重试复用现有 `calcDims()`。
- **验收**：Node 层直接测 `classifyGenError` 四类各一条；真机用"故意填 8192×8192"验证 OOM 分支。
- **成本**：2~3 天。**风险**：低。

### 第二批（P1，约 2 周）：把"出图"变成"调图"

#### 2.1 种子工具条

- **做**：种子胶囊旁边加三个小按钮：`+1`（当前种子加一）、`🎲`（重掷）、`↩`（取上一张的种子）。
  固定模式下才启用；随机模式下点 `↩` 会自动切到固定。
- **技术落点**：`planSeed()` 加 `mode: 'bump'` 分支，或直接在面板层处理（读 `gen.seed`，
  写回 `gen.seed + 1` 并切 `fixed`）。**不动生成链路**。
- **验收**：e2e 点 `+1` 后 `gen.seed` 精确 +1 且 `seedMode === 'fixed'`；
  点 `↩` 后种子等于最近一条 run 的 seed。
- **成本**：2 天。**风险**：低。

#### 2.2 参数预设

- **做**：面板顶部加一个下拉：「预设」→ 列出已存的参数组合（画幅/尺寸/张数/种子模式/工作流）。
  可「存为预设」「删除」。存 localStorage（和 `panelSide` 一样），不占服务端。
- **和"工作流库"的区别**：工作流库存的是**图**，预设存的是**面板上的那排参数**。
- **验收**：存一套 → 换节点 → 选中预设 → 五个参数全部套用；刷新后预设还在。
- **成本**：3 天。**风险**：低。

#### 2.3 生成前的尺寸/显存校验

- **做**：提交前用 `/system_stats` 的显存估算：`4K` 或 `> 4MP` 时给
  「预计 X GB / 本机 Y GB」的确认框，而不是现在只写"本地偏慢"。工作流 `sized=false`
  时也明确说"这张工作流不接受尺寸，实际出图由它决定"。
- **技术落点**：`/api/health` 已经返回 `ram_total`；`/system_stats` 有 `vram_total`。
- **验收**：真机在 8G 显存机器上选 4K → 弹出预警；e2e 用桩数据断言文案。
- **成本**：2 天。**风险**：估算不准会误报，所以做成"提示"不是"阻止"。

### 第三批（P2，约 3 周+）：把"调图"变成"改图"

#### 3.1 并排对比

- **做**：多选 2~4 个图片节点 → 对齐悬浮条旁边出现「对比」→ 打开一个并排视图
  （复用大图 lightbox 的容器，改成网格 + 同步缩放/平移）。每格下方带参数摘要，
  点「采用」把那张设为某个节点的当前图。
- **技术落点**：lightbox 已经支持多图列表和信息卡，扩展成"多来源"即可。
- **验收**：选 3 个节点 → 对比视图 3 格 → 缩放同步 → 点某格「采用」后目标节点换图。
- **成本**：1~1.5 周。**风险**：中（要处理不同宽高比的排布）。

#### 3.2 局部重绘（蒙版）

- **前置条件**：需要一个带 `LoadImageMask` / `VAEEncodeForInpaint` 的 API 工作流。
  **这个还没有确认**——没有它只能做"涂抹 + 导出蒙版"，跑不了。
- **做**：图片节点进涂抹模式 → 画蒙版 → 导出黑底白区 PNG（尺寸 = 原图像素）→
  上传（复用 `/api/upload`，服务端零改动）→ 跑 inpaint 工作流 → 结果作为新的一条 run。
- **验收**：1024² 图上涂中间一块，出图只有那块变化；蒙版尺寸断言（不是 380 宽）。
- **成本**：1~1.5 周（工作流就绪的前提下）。**风险**：中高，依赖工作流。

## 四、排期建议

```
第一批（队列 + 错误分类）  ← 先做，它让后面所有功能都"可观察"
        │
第二批（种子 + 预设 + 尺寸校验）  ← 调图高频动作，纯前端为主
        │
第三批（对比 → 局部重绘）  ← 对比不依赖外部；重绘等 inpaint 工作流
```

和现有计划的冲突点：

- 第一批会和 `ROADMAP` v1.1 的「假 ComfyUI 进 CI」抢同一块（都要动 `server.py` 的代理层）。
  **建议先做假 ComfyUI**，队列/重试的 e2e 才有地方跑。
- 第三批的对比视图会碰 `#lightbox`，和刚做完的右侧抽屉是同一处，**先做抽屉再做对比**（抽屉已完成）。

## 五、明确不做

| 不做 | 原因 |
|---|---|
| 提示词 LLM 扩写 | 本地没有模型网关，要接就得联网或依赖用户装 LLM 节点；工作流里自带扩写节点的话已经能用 |
| 提示词语法高亮 / 权重编辑 | ComfyUI 侧才是权威解析方，前端高亮容易和它不一致 |
| 云端排队 / 多机分发 | 单机工具，没有账号体系 |
| 自动调参（AI 选最佳） | 需要评估模型，没有客观标准，做出来是玄学 |

## 六、需要你拍板的两个问题

1. **队列面板要不要支持"重排/插队"？**
   支持 = 要维护自己的队列顺序并逐条提交（复杂度上一个台阶）；
   不支持 = 只做"全部提交 + 看进度 + 取消"（够用，ComfyUI 自己也是 FIFO）。
   **我建议先不做重排。**

2. **参数预设存哪儿？**
   - localStorage（跟着浏览器，换机器就没了，但零改动）
   - 服务端 `data/presets-ui.json`（跟项目走，多台机器共享，需要加一个路由）

   我倾向**服务端**——你已经有多台机器在用的迹象（GitHub 下载、另一台机器），
   参数组合属于"工作资产"，不该只活在浏览器里。
